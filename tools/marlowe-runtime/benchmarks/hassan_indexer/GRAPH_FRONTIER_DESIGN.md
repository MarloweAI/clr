# GPU graph completion and host retirement

## Objective and evidence

Preserve the original Hassan application, captured graph, kernels and stream/event calls while making parallel dispatch cheap. Jobs55382/55399/55418 identify reset and fence costs plus a combined boundary architecture: hidden CPU reads during GPU-local signal reset; repeated fence work at graph boundaries; and redundant entry/public retirement work between consecutive graphs. The third contrast combines entry-packet removal, private completion placement and deferred host retirement; it does not independently attribute their effects. The last same-object local contrast is14.994→11.732us/pair atg1,21.75% lower, while g50 stays7.23us. This is sufficient architectural headroom to investigate an actual HIP implementation. It is not an application win, and the g50 synthetic result alone remains insufficient.

The design principle is to represent GPU dependency readiness separately from CPU-observable retirement. A graph finishes on a private GPU token immediately. Its host command/resources remain in CLR's normal submission batch until an ordinary completion proves safe retirement. A following eligible graph may consume that private token directly; any intervening observable operation uses the ordinary completion path. There is no application-level batching API, graph splitting, kernel-size threshold or prediction of future launches.

## Existing implementation and reuse points

The diagnostic W/source at HIP69f3df4 uses GraphExec::RunGraphSignals (hip_graph_internal.cpp2438). It GPU-resets a generation, constructs ordinary AccumulateCommands for each logical lane, seals them all, then enqueues a final ordinary Marker with a callback. It excludes g1 because that graph has no internal cross-queue edge (CanUseGraphSignals2329). This safe per-lane retirement explains why changing only token location does not address short boundaries. The source has real entry-frontier correctness fixes; these must remain.

CLR already supports deferred host retirement for ordinary commands. Command::enqueue (rocclr/platform/command.cpp357) forms a submission batch and flushes immediately for markers and CL_COMMAND_TASK; other commands submit then use FlushSubmissionBatch. AccumulateCommand is CL_COMMAND_TASK (command.hpp1414), so it currently forces that immediate path. HostQueue::FormSubmissionBatch (commandqueue.hpp261) retains commands, records the last command and links them into the batch; FlushSubmissionBatch (commandqueue.cpp144) enqueues an ordinary marker at the existing batch watermark. Event::notifyCmdQueue (command.cpp264) materializes an ordinary marker when a command has no HwEvent. HostQueue::finish (commandqueue.cpp172) flushes pending batches. hipStreamQuery_common (hip_stream.cpp546) considers fence state and then notifies the last command; callbacks similarly capture the last command. These are promising shared mechanisms, not proof that every boundary is already covered.

## Proposed representation

1. An explicit graph-dispatch command enters the ordinary host submission batch without forcing per-graph IRQ/host completion. Prefer a narrowly named internal defer-batch property with a normal command type over pretending a graph is a different public command type. It is enabled only on the reviewed HIP direct-dispatch path, with profiling/tracing incompatible paths falling back.
2. Each launch owns a fresh or fully retired generation of private GPU signals and immutable packet/argument snapshots. Reset uses a cached API-typed value pointer and a proven publication fence, never a hot hsa_signal_store metadata lookup. No CPU wait, IRQ handler, native admission history or ordinary HwEvent may receive an internal GPU-only handle.
3. The launch has a private graph-final token after all branches and required SYSTEM release. The launch stream records that token together with a strong owner lease. Consecutive eligible graph commands retain the predecessor lease before using its token, import required visibility and chain their final frontier without a redundant main entry. The next call need not exist when the first is submitted.
4. An ordinary command/observation invalidates private chaining and bridges the exact logical boundary through the normal completion machinery. A marker on the main queue is sufficient only after the graph's final join has covered every side lane and reader. Recording the last command, queue progress and pending batch must never let query return success early.
5. Host batch retirement releases launch commands and graph/module/argument references. A generation can return to the pool only after every command and successor token-consumer lease is gone and valid GPU retirement has been proven. Completing the producer's CPU callback alone is insufficient if a later consumer still holds its token. A pending frontier itself must retain a lease until cleared or transferred.

The first implementation should be confined to flat, enabled, captured kernel graphs on one agent, known distinct physical queues, compatible AGENT-or-stronger releases, no hidden heap/host/copy nodes, direct dispatch and profiling disabled. Eligibility follows semantics, not tensor shape, kernel size or a performance threshold. Ineligible work uses the existing path. Extending beyond that set is a separate correctness proof.

## Source-specific changes required before implementation

- Replace the current internal-cross-queue-edge eligibility test (hip_graph_internal.cpp2380–2389) with eligibility for a proven all-lane GPU final join. The old test rejects g1, which is the exact new target. Keeping it would silently preserve the regression regardless of other changes.
- Give each online launch its own frontier token (segments+1 or equivalent). The probe uses the next graph's preallocated entry token as completion, but an online runtime cannot depend on a future launch existing. A successor retains the predecessor's generation/lease before consuming its frontier.
- Cached CPU reset replaces only initialization. The current reset AccumulateCommand also supplies a launch-stream predecessor event. First/nonchained launches must snapshot/import that exact public predecessor into every root lane; chained launches consume the predecessor-owned private frontier. CPU stores and SFENCE do not establish a stream dependency.
- Implement the reviewed acquire-only first-kernel upgrade explicitly. Existing addSystemScope in rocvirtual.cpp1511–1533 also upgrades the batch-tail release, so reusing it would change the proven scopes and the measured cost. Synthesize a final AGENT-acquire/SYSTEM-release join that covers all terminal physical lanes. Collapse aliases and, for more than five dependencies, prove an ordered barrier sequence/tree with only the final SYSTEM release.
- Add an explicit serialized frontier transition before a nonchain command is submitted. Command::enqueue submits before its subsequent FlushSubmissionBatch call; batch ownership and a later watermark are not a GPU dependency. Generic markers from notify/finish/query must bridge the private token associated with the exact observed boundary. Main-queue adjacency is sufficient only for the paths whose all-side join and ordered successor have been proved; copy/SDMA/other lanes cannot inherit this assumption.
- Preserve public event boundaries exactly. A record/query/callback after launch A must not accidentally use a later frontier B. Event state stays pending with no ordinary HwEvent until its associated private completion is bridged. Pending CPU callbacks/token-zero cannot alone recycle storage that a successor still reads.

## Obligations before code is ready

- Audit every route that can obtain or follow a graph completion: stream/device sync and query, event record/wait, callbacks and host nodes, legacy default-stream interactions, ordinary compute/copy commands, cross-stream/device/SDMA dependencies, stream destruction and asynchronous error propagation. Exact public event boundaries must not silently become the final boundary of a later batch.
- Confirm one shared notification/batch hook covers these routes. Add narrowly scoped hooks only where source inspection proves a gap. Raw queue progress alone is not host-visible work; fence_dirty alone is not a reliable substitute for a pending graph command.
- Prove lock order before calling side-queue submission under the main queue execution lock. GraphExec launch serialization, host batch extension and queue/physical-queue alias handling must not introduce deadlock or overwrite the recorded frontier during concurrent calls.
- Prepare packet copies, signal arenas, callbacks and ownership bookkeeping before first publication. Failed partial publication must join every touched lane and retain/quarantine all storage until safe; do not free a graph because an API call returned an error. Respect queue capacity with a topological publication order that cannot block on a producer the host has not submitted.
- Graph update/disable/alternate launch stream, executable destruction before synchronization, input/module/tensor lifetimes and arena reuse need explicit ownership fixtures. Changing an executable while earlier launches exist must not mutate their snapshots or token graph.
- Bound retained commands/arenas through the existing batch watermark or a resource-capacity rule. This is a resource bound, not a workload-specific performance heuristic. Idle streams need an ordinary retirement path; no unbounded retained graph pool or orphaned callback.

## Validation and stop conditions

Build an immutable default-off diagnostic with same-byte on/off controls. First run untimed asynchronous input visibility, intermediate event/query/callback, ordinary command/copy insertion, two streams, multiple in-flight generations, update/disable/destroy, concurrent submit/observe, ring-wrap/capacity and partial-publication failure fixtures. Exact-path receipts must prove the g1 graph actually uses the new path, all GPU dependencies stay private and public completion covers every lane.

Then run unchanged warm Hassan g1/g50 serial and two-stream benchmarks against stock and the preserved prior best, with traced proofs separate from timing. A new lower-layer number is not success. Continue only if actual g1 improves with genuine overlap and g50 is retained; then validate the broader microbenchmark holdouts and Hassan's unchanged serving benchmark as required by Goal1. Full production qualification is separate. If integration cannot preserve semantics or loses the measured headroom, checkpoint and move to Goal2 rather than add shape heuristics.
