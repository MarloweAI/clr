The reduction uses `(event - polling) / (event - no_waiter)`, not a 90–93% reduction in total runtime. Total reductions are 36.76% and 51.55%. The quoted conversation says a real-model test was planned; it supplies no completed model result or controlled graph-splitting comparison.

Our matched [split-Q/K experiment](POLLING_CONTROL_RESULTS.md) is consistent with a useful polling effect: event waits 30.263 → GPU polling 20.993 µs/pair (−30.63%). Those same split boundaries still cost more than the unsplit two-stream graph, 14.254 µs/pair, and split serial, 18.465 µs/pair. All are from job 54181's own protocol. Do not substitute historical timings from a different protocol. Breaking the graph and changing how waits execute must be attributed separately.

A plausible explanation is reduced interference while a dependency is pending, amortized over a long producer. Frequent short Q/K joins also need a cheap handoff. A polling-kernel dispatch, graph entry/exit, signal writes and fences can outweigh that saving. This is a mechanism consistent with the evidence, not a decomposition of Hassan's reported total time. The [tested internal GPU helpers](GRAPH_PREWAIT_RESULTS.md) regressed; this rejects those implementations, not every possible GPU-assisted synchronization architecture.

Prior same-signal job 45006 already gives supporting low-level evidence: in approximately 8 ms waiting-only windows, pending AQL generated about 1.23 million summed CPC cache-interface counts versus 56.7 thousand for native prewait plus the original dependency. Pending duration increased AQL interface activity without comparable growth in packet-decode counts. That is evidence of sustained activity on the wait path, not bandwidth saturation, an address-specific transaction count, or a firmware instruction trace. Its source/results remain at `amd-runtime-production/results/cp-wait-profile-45006/REPORT.md`; no counter experiment was repeated here.

| Interface | Useful observation | Missing boundary / restriction |
|---|---|---|
| HSA dispatch profiling | Dispatch processing start/end in the HSA system clock domain | No separate timestamp for signal decrement visibility, barrier satisfaction or queue eligibility |
| Device-wide CPC counters | Pending-path activity; decode, interface and stall event totals | Counts cover the collection window, not individual joins, addresses or firmware instructions; previously zero stall counters lacked positive calibration |
| Dispatch-level thread trace | Shader wave/instruction execution | The inspected SDK starts its dispatch trace through `enable_serialization()`; it is unsuitable for validating unchanged concurrency |
| Device-level thread trace | Shader execution across a selected agent without that dispatch-serialization path | Creates its own control queue; requires perturbation controls and actual gfx950/decoder verification. Published records expose waves/instructions/SQ counters, not a CP barrier-recognition event |
| PC sampling | Statistical observations of executing shader waves | Does not expose an instruction stream for the command-processor waiter; cannot time an interval with no shader wave |
| Host observation of real completion signals | Proof that the CPU saw both completed values by a recorded time | CPU visibility is not the consumer command processor's observation time; cross-clock conversion error must be measured |

[AMD's versioned thread-trace documentation](https://rocm.docs.amd.com/projects/rocprofiler-sdk/en/docs-7.2.0/how-to/using-thread-trace.html) describes shader execution tracing and SQ-only streamed counters. The public record types also include shader/realtime clock pairs, but those do not by themselves calibrate every XCD or align shader time to host time. No generic `rocprofv3 --att` run is planned as a barrier/firmware trace.

## Clock check and the next measurement contract

The old receipts cannot supply an absolute CPU-ready → GPU-start delay. `ready_omit_probe/replay.cpp` uses `CLOCK_MONOTONIC_RAW`. Pinned ROCr's HSA system timestamp uses `CLOCK_BOOTTIME`; its dispatch timestamps translate the GPU counter through KFD clock pairs. These are different clocks even when both have nanosecond units. The retained arrays have an approximately 4.14-second origin difference, not a negative multi-second hardware latency. Fitting that offset from the desired causal ordering would manufacture the answer.

Pinned source: [HSA system clock implementation](https://github.com/ROCm/rocm-systems/blob/97f5574fe2fdc7bef44fb01545347912ee9f1779/projects/rocr-runtime/runtime/hsa-runtime/core/util/lnx/os_linux.cpp#L779), [GPU-to-system conversion](https://github.com/ROCm/rocm-systems/blob/97f5574fe2fdc7bef44fb01545347912ee9f1779/projects/rocr-runtime/runtime/hsa-runtime/core/runtime/amd_gpu_agent.cpp#L2135). The conversion comments discuss clock-pair certainty below about 4 µs and limiting extrapolation error to about 0.5 µs. They are implementation comments, not a measured error guarantee for our runs. Fixing RAW versus BOOTTIME alone does not remove GPU-to-host correlation error.

The next admissible diagnostic is a clock-qualified completion observation, not another scheduler variant:

1. **Capability/calibration first.** Use the same mapped HSA bytes and exact allocated GPU. Before any timed replay, bracket HSA system-clock reads with RAW and BOOTTIME reads; record frequency, resolution, every bracket and errors. Separately bracket KFD GPU/System clock queries and compare returned GPU ticks through `hsa_amd_profiling_convert_tick_to_system_domain`. Repeat before/after each observation batch. Retain wide brackets; report uncertainty rather than treating a midpoint as ground truth. Verify the counter belongs to the same agent and clock domain. Repeated samples, low variance, minimum round-trip time and conversion consistency do not establish a conservative absolute-error bound or remove systematic GPU/System-pair uncertainty. A documented driver bound or an independently validated clock tie is required. If the available API/driver path cannot bound correlation tightly enough, stop at that finding; do not launch Q/K solely to collect more uncalibrated timestamps.
2. **Original packets, observational host only.** Preserve the 400 original Q/K kernel packets, dependencies, fences, distinct queues and full prepublication from mode 0. Compare no per-layer observer with the existing mode-1 observer; do not make the host publish dependent work. After acquire loads of BOTH real predecessor signals return zero, record a timestamp directly with `hsa_system_get_info(HSA_SYSTEM_INFO_TIMESTAMP)` (or equivalently scaled BOOTTIME after validation). The timestamp must follow both zero reads. Keep RAW/BOOTTIME/HSA bracketing as an independent audit, not a fitted offset for this causal receipt. Keep independent signal lifetimes through final drain. No kernel modifications or added polling shader.
3. **Predeclared validity gates.** Calibration must support a conservative total uncertainty at most 1 µs to discuss the approximately 5 µs dispatch-end-to-next-start interval; this is a capability-failure gate, not a runtime heuristic or an accuracy claim already established by the listed APIs. The source comments alone suggest an uncertainty window comparable to the interval of interest and cannot clear this gate. A calibration discontinuity invalidates that batch's cross-domain attribution. Retain observer-off and profiling-off timing controls, repeated order, numerical outputs and exact hashes. Do not attribute a sub-uncertainty effect or assume the observer is free. No production result follows from this diagnostic.
4. **Permitted claim.** Let `O` be the HSA-domain receipt after both zero reads and `E` the adverse bound on total timing uncertainty. For each successor, compute `L = S_profiled_start - O - E`. Only positive `L` is a lower bound on time remaining after CPU-visible both-zero completion. Use the earlier successor start for time until the first dispatch, and the later start for time until both; calculate per pair before aggregation. Late CPU polling shrinks the bound; zero/negative results are inconclusive. This can rule out producer-to-CPU completion publication alone explaining the entire interval. It does not prove that the consumer CP had seen zero or was eligible to run. It still cannot distinguish CP visibility/recognition, acquire work, queue arbitration and dispatch admission. If the bound is inconclusive, say so; do not retune the observer to force it.

If this public observation remains insufficient, the internal request to AMD should be concrete: on the frozen direct-AQL reproducer, capture producer completion publication, consumer barrier recognition, queue eligibility and next dispatch admission in one calibrated device clock, with independent-queue progress and trace-off controls. Preserve the packet bytes, kernel ELFs, scopes and signal addresses; compare already-ready and delayed dependencies. Ask for a supported instrumented firmware/driver build and its perturbation bounds. No request has been sent, and no firmware/driver change or shared-node reboot is authorized by this document.
